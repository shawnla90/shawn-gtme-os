**low effort**

- format a file
- quick regex

fast, focused, cheap. if the task fits in one sentence, it's probably low.

**medium effort**
- write a new function with a clear spec
- debug a specific error with a stack trace attached
- add a feature that touches 2-3 files
- refactor a module you've described well
- write tests for existing code

this is the workhorse. probably 70% of what you actually do in a day lives here.

**high effort**
- architect a new system from scratch
- debug something where you genuinely don't know where the bug is
- review an entire codebase for a specific class of issue
- write a complex multi-step migration
- anything where the context window needs to breathe

the difference isn't just speed. high effort changes how the model reasons through ambiguity. it'll backtrack, reconsider, explore edge cases you didn't mention. that's exactly what you want for hard problems and actively harmful on easy ones because it introduces second-guessing where none was needed.

opposite problem is more common though. people set everything to high, wonder why responses are slow, and then blame the model when the real culprit is asking it to over-engineer a one-liner.

the mental model that helped me: high effort is for unknown unknowns. medium is for known unknowns. low is for knowns. if you already understand the problem fully and just need execution, save the compute.

## 10. [CONTRARIAN] AI coding burnout isn't a model problem. it's a task management problem.

### REDDIT Version

AI coding burnout isn't a model problem. it's a task management problem.

I keep seeing the same post: "Claude is making me anxious, I'm just watching it spin, I don't know when to interrupt, I've lost hours to context drift."

and every time I read it, I think . that's not the model. that's a workflow without rails.

here's what's actually happening when you hit that wall:

you're giving the agent a vague task, watching it work, second-guessing it mid-run, interrupting to redirect, losing the thread, starting over. repeat for 4 hours. that's not AI fatigue. that's you running an asynchronous worker like it's a synchronous conversation.

the model isn't anxious. you are. because you didn't define done before you started.

what actually fixed it for me:

**1. task scope before you type anything**

I write one sentence that defines the exit condition. not "refactor the auth module" . "refactor auth so that login.py imports from a single auth.py and all tests pass." the agent can't be done until that's true. you can't be anxious about where it's going because you already know.

**2. stop watching**

this one is uncomfortable but it's the whole thing. you set the task, you walk away. you come back when it stops. watching an agent work in real-time is like watching paint dry and then blaming the paint for making you bored.

if you can't walk away, the task is too vague.

**3. the interrupt rule**

I only interrupt if the agent is about to do something I can't undo. deleting files, pushing to prod, dropping a table. everything else . let it finish. reviewing a completed wrong answer is faster than course-correcting mid-run 100% of the time.

**4. context windows are not sessions**

people burn out because they're treating one context window like an infinite work session. it's not. it's a sprint. each context has a job. when it fills, the sprint ends, you review, you hand off to a new context with a clean summary. once you think this way the "losing context" problem mostly disappears.

the stress posts are real. I don't think people are exaggerating. but the solution everyone is waiting for . a better model, longer context, faster responses . that's not it.

the solution is spending 10 minutes before every session writing down what done looks like. then trusting the machine to get there.

the agent is fine. the rails are missing.
