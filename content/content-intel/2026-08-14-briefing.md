what a real loop orchestrator looks like (not a demo, an actual production setup)

most posts about loop orchestration with Claude Code show you a while loop with a sleep and call it done. here's what mine actually looks like after running it in production for a few months.

---

**the schema first**

everything lives in SQLite. one table:

```sql
CREATE TABLE loops (
 id TEXT PRIMARY KEY,
 name TEXT NOT NULL,
 trigger_type TEXT CHECK(trigger_type IN ('cron', 'file', 'webhook', 'manual')),
 trigger_config TEXT, -- JSON
 prompt_path TEXT NOT NULL, -- path to the .md file Claude reads
 last_run_at INTEGER,
 last_run_status TEXT CHECK(last_run_status IN ('ok', 'failed', 'skipped', 'running')),
 last_error TEXT,
 run_count INTEGER DEFAULT 0,
 consecutive_failures INTEGER DEFAULT 0,
 context_path TEXT, -- optional: inject this file into every run
 cooldown_seconds INTEGER DEFAULT 0,
 max_failures INTEGER DEFAULT 3,
 enabled INTEGER DEFAULT 1
);
```

the two columns most people skip: `consecutive_failures` and `context_path`.

`consecutive_failures` is how you avoid burning through tokens on a broken loop. once it hits `max_failures`, the loop disables itself and writes a row to a `loop_alerts` table. nothing pages me, I just see it when I open my dashboard. works fine for async stuff where missing a few runs doesn't matter.

`context_path` is where compounding comes from. every loop run can point at a file that gets injected as context before the prompt. mine update over time. the enrichment loop writes a summary of what it found back into the context file, so the next run knows what's already been processed, what patterns emerged, what domains came back clean vs. bounced. the loop gets smarter without touching the prompt.

---

**trigger handling**

I have a single dispatcher script. it wakes up every 60 seconds, pulls all enabled loops, and routes them:

```python
def should_run(loop: dict) -> bool:
 now = int(time.time())

 if loop["trigger_type"] == "cron":
 return cron_is_due(loop["trigger_config"], loop["last_run_at"])

 if loop["trigger_type"] == "file":
 config = json.loads(loop["trigger_config"])
 path = config["watch_path"]
 last_modified = os.path.getmtime(path) if os.path.exists(path) else 0
 return last_modified > (loop["last_run_at"] or 0)

 if loop["trigger_type"] == "webhook":
 # webhook handler writes a pending row to loop_triggers table
 return has_pending_trigger(loop["id"])

 return False # manual only runs via explicit call
```

the file trigger is the one I use most. a scrape writes a file, the loop sees it changed, picks it up. no pub/sub, no queues. SQLite is the queue.

---

**failure handling in practice**

when a loop fails I write the error, increment `consecutive_failures`, and check against `max_failures`. if it trips:

```python
db.execute("""
 UPDATE loops SET enabled = 0, last_run_status = 'failed'
 WHERE id = ?
""", [loop["id"]])

db.execute("""
 INSERT INTO loop_alerts (loop_id, error, tripped_at)
 VALUES (?, ?, ?)
""", [loop["id"], error_message, int(time.time())])
```

I check `loop_alerts` in the morning. most alerts are rate limits or a broken API response that fixed itself. re-enabling is one SQL update.

the thing that surprised me: most loops don't fail on the Claude call. they fail because the output file didn't write where expected, or the input file was empty, or a dependency wasn't running. so I added a pre-flight check per loop:

```python
def preflight(loop: dict) -> tuple[bool, str]:
 config = json.loads(loop.get("trigger_config") or "{}")
 
 if "requires_file" in config:
 path = config["requires_file"]
 if not os.path.exists(path):
 return False, f"required file missing: {path}"
 if os.path.getsize(path) == 0:
 return False, f"required file is empty: {path}"
 
 return True, ""
```

skip the run cleanly instead of burning a token call to get back an error about missing input.

---

**why it compounds**

the context injection is the main thing. but the other piece is that every loop writes structured output, not prose. my enrichment loop writes back to the same SQLite database. my scoring loop reads from enrichment. my outreach loop reads from scoring and checks a `do_not_contact` table before it does anything.

each loop is dumb in isolation. together they form a pipeline that maintains state without any of the individual loops caring about the full picture.

I've added 11 loops over the past few months. adding a new one is: write a prompt .md file, insert a row into the loops table, define the trigger. done. the dispatcher picks it up automatically.

---

**the prompt files**

each loop has its own .md file. the dispatcher reads it, prepends the context file if one is set, and passes it to the Claude CLI with `--print` for non-interactive runs. the prompt files are version controlled. when a loop drifts or starts producing weird output, I can diff the prompt history.

structure I use:

```
## goal
one sentence.

## input
what file or data you'll receive and what format it's in.

## rules
numbered list. edge cases live here.

## output
exact format. if it's JSON, include the schema. if it's a file write, include the path pattern.
```

no fluff in the prompts. Claude doesn't need encouragement, it needs a spec.

BLOCKED_PATTERNS = [
