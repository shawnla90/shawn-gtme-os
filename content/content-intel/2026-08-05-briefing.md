**the review prompt**

after Codex outputs, paste this into your Claude Code session:

```
Review the code above as a senior engineer doing a PR review. Be specific:

1. Correctness: does it actually solve the stated problem? what edge cases does it miss?
2. Logic errors: walk through the execution path and flag anything that breaks
3. Test coverage: what inputs would make this fail that aren't tested?
4. Implementation quality: anything that would cause a code review rejection?

Output your critique as numbered issues. Don't rewrite the code yet.
```

then feed the numbered critique back into Codex:

```
Fix issues 1, 3, and 4 from the review above. Leave issue 2 . I'll handle that separately.
```

the "leave issue 2" instruction matters. asking Codex to fix everything at once produces lazy patches. targeted fixes are cleaner and easier to verify.

**why the split works**

Codex is fast at generation. Claude is better at finding the thing that looks right but breaks on unexpected input, the off-by-one, the async timing issue that only shows under load. they're not competing. they're different strengths running in sequence.

**the full loop**

1. Codex generates → paste output into Claude Code context
2. Claude reviews with the prompt above → numbered critique
3. scan the critique, decide which issues are actually critical
4. Codex fixes the flagged ones → paste updated code back into Claude Code
5. Claude does a final verification pass: does the fix actually address the issue?
6. ship

step 5 is the one most people skip. the verification pass after the fix is where regressions get caught before they hit the test suite.

**on running both simultaneously**

I keep both open all day. when one hits a rate limit the other is still running. that's the whole reason for two terminals. it's not about having two AI opinions, it's about no downtime on the review loop.

here's the session, the schema, and the three things I had to go back and fix manually because Claude Code got them right-ish and not right.

**the session**

single starting prompt:

"build me a social listening tool that monitors reddit posts and comments for intent signals around [topic], writes to SQLite, scores each post 1-5 for buying intent, and logs what it found with a timestamp"

Claude Code asked two clarifying questions . which subreddits, and did I want comment-level signals or just top-level posts. I said both. It scaffolded the whole thing: `monitor.py` entry point, `db.py` with schema creation, `scorer.py` with a scoring prompt, `requirements.txt`.

total lines written by Claude Code: ~340.
total lines I touched: 11.

**the schema it built**

```sql
CREATE TABLE posts (
 id TEXT PRIMARY KEY,
 subreddit TEXT,
 title TEXT,
 body TEXT,
 url TEXT,
 author TEXT,
 score INTEGER,
 created_utc REAL,
 fetched_at REAL,
 intent_score INTEGER,
 intent_label TEXT,
 flagged BOOLEAN DEFAULT 0
);

CREATE TABLE signals (
 id INTEGER PRIMARY KEY AUTOINCREMENT,
 post_id TEXT,
 signal_type TEXT,
 signal_text TEXT,
 confidence REAL,
 created_at REAL,
 FOREIGN KEY (post_id) REFERENCES posts(id)
);
```

clean. sensible. I would have written almost the same thing.

**what broke**

**1. duplicate ingestion**

the tool was pulling from "hot" and "new" feeds separately on a cron. posts that appeared in both feeds hit the INSERT statement twice. Claude Code used `INSERT OR IGNORE` on the primary key, so duplicates weren't creating bad rows . but `fetched_at` wasn't updating either. I wanted to know when something showed up in both feeds, which is actually a signal. changed it to `INSERT OR REPLACE` and added a `feed_source` column to track which feed caught it first.

**2. intent score drift**

the scoring prompt Claude Code wrote was solid, but it had no anchor examples. on run 1, "how do I get started with X" scored a 3. on run 6, same phrasing scored a 1. no few-shot anchors baked into the classification call, so the LLM was improvising its own scale each time. I added four examples directly to the scoring prompt . two high-intent, two low-intent . and the scores stabilized immediately.

if you're running Claude on any recurring classification pipeline, anchor your prompts with concrete examples or your outputs will drift across runs. this is the thing nobody mentions in the vibe-coded tool posts.

**3. the deleted post problem**

reddit deletes posts. the tool was hitting 404s on posts it had already fetched but was trying to re-fetch for updated comment counts. Claude Code had error handling, but it was just logging the error and moving on. nothing in the schema tracked deletion status. so I had a growing list of posts with stale comment counts and no way to tell which ones were gone.

added a `deleted_at` column. updated the error handler to write a timestamp there instead of logging to the void.

what Claude Code nailed: schema shape, scraping logic, error handling structure, modular file organization. what it couldn't nail: the product decisions I hadn't worked through yet. do I care which feed caught the post first? yes, actually . but I didn't know that until the data showed me.

it's a context boundary shift.

when you send text, the model is inside its primary reasoning channel. refusals live there. rules live there. switch to image input and you've changed the modality entirely. the model shifts into interpretation mode. it's reading a different kind of document now.

builders who use Claude Code daily feel this intuitively but rarely name it: the format of your input changes how the model processes it.

seen this in real work. paste a wall of JSON instructions and you get refusals or misfires. reference that same JSON as a file attachment and you get cleaner parsing, better execution. write a prompt in imperative language and the model argues back. write the same prompt as a spec with a goal state and it builds toward the goal.

the model forms a mental model of who sent the input and what kind of document it is before it ever processes your actual request. text prompts get classified as user instructions. screenshots get classified as reference material showing an existing state. that classification gap changes everything downstream.

this is why good prompting isn't about finding magic words. it's about framing the context so the model builds the right internal representation before it starts reasoning.

builders who internalize this:
- structure prompts like specs, not commands
- give it the artifact, not a description of the artifact
- let the file carry the complexity, let your words carry the intent

the safety argument is worth having separately. context-shifting clearly exposes real gaps and I'm not dismissing that.

but if your takeaway is "Claude is broken" you're leaving the actual lesson on the table.

these models don't have one reasoning mode. they have several. knowing which one you're activating is the whole game.
