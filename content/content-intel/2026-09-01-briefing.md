treat MEMORY.md as your working memory. if it's not in there, assume it's forgotten.

Claude Code loads `MEMORY.md` on every session start automatically. you're not building a custom retrieval system or a vector store. you're just using the file that's already getting injected, and giving the agent explicit instructions to keep it current.

the built-in usage dashboard tells you what's left. it doesn't tell you which session torched it, which task type is running hot, or whether your burn rate changed between weeks. that's not a dashboard. that's a gas gauge with no mpg readout.

if you're not instrumenting this yourself, you're flying blind.

here's what I log on every turn:

```python
import anthropic
import sqlite3
from datetime import datetime

def log_usage(response, task_label: str):
 conn = sqlite3.connect("token_log.db")
 conn.execute("""
 CREATE TABLE IF NOT EXISTS usage (
 id INTEGER PRIMARY KEY,
 ts TEXT,
 label TEXT,
 input_tokens INTEGER,
 output_tokens INTEGER,
 cache_read INTEGER,
 cache_write INTEGER
 )
 """)
 u = response.usage
 conn.execute(
 "INSERT INTO usage VALUES (NULL,?,?,?,?,?,?)",
 (
 datetime.utcnow().isoformat(),
 task_label,
 u.input_tokens,
 u.output_tokens,
 getattr(u, "cache_read_input_tokens", 0),
 getattr(u, "cache_creation_input_tokens", 0),
 ),
 )
 conn.commit()
 conn.close()
```

call it after every API response. takes two seconds to add. the payoff is that you can now ask: which task label is burning the most? are my cache reads actually landing? did something spike yesterday vs. the same day last week?

a few things that surprised me when I started tracking:

- **file attachment abuse is the silent killer.** attaching the same large file across multiple turns instead of referencing a cached version will quietly 3-4x your input token cost per session. you won't see it in the dashboard. you'll just hit the wall early.
- **cache misses compound fast.** if your system prompt isn't hitting cache consistently, you're re-paying for it every turn. log `cache_read_input_tokens` and compare it to `input_tokens`. if cache reads are low relative to input, your prompt structure isn't cache-friendly.
- **week-over-week burn rate is the metric that matters.** not total remaining. rate. if you're consuming 40% more tokens per session this week than last, something changed and you need to find it before the limit finds you.

the anthropic counter resets your limit. your SQLite log explains why you hit it.

doesn't need to be fancy. even a CSV append works. just write it down. every turn. every task.

that's not vibe coding. that's reactive prompting. and yeah, that's chaos.

here's the actual difference.

when I spin up a new feature, the agent gets a spec before it writes a single line. not a novel . a job brief. what it's building, what it's NOT allowed to touch, what done looks like. three paragraphs max.

```
# task: add email validation to signup flow
scope: /src/auth/signup.ts only
do not touch: /src/auth/login.ts, /src/auth/session.ts
done when: unit tests pass, no new console.errors in the browser
```

that's it. the blast radius is defined upfront. the agent can't wander into session management and "helpfully" refactor something I didn't ask for.

second thing: tests before code. I tell the agent to write the tests first based on the spec, then implement against them. suddenly it has a target. it's not guessing what "good" looks like . it knows.

third thing: check-ins, not full sends. I break the work into chunks. agent writes the validation logic, stops, shows me. I check. then it writes the error states. stops, shows me. you wouldn't hand a junior dev a two-week sprint and say "come back when it's done." same applies here.

the blast radius concept is the one most people skip. your agent will do exactly what you allow it to do. if you give it access to the whole repo and a vague instruction, it'll use the whole repo. if you scope it, it stays scoped.

none of this is complicated. it's just treating the tool like a team member instead of a magic box.

the "vibe coding is hard" people aren't wrong that their experience is hard. they've just optimized for speed on the first request and are paying for it on every request after.

put the rails up first. the vibe gets a lot smoother.
