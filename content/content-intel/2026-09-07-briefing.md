- reviews Codex output before merge
- long tasks: use think mode

## Codex (execution)
- receives task briefs via TASK.md in the relevant directory
- never modifies CLAUDE.md
- never makes architectural decisions without a brief

**Target sub:** r/r/ClaudeCode
**Scores:** viral=7 voice=10 gap=8 effort=high

### REDDIT Version

spawning agents is the easy part. keeping them from stepping on each other is the actual engineering problem.

I run three models in parallel most days . Sonnet (via Fable), Opus 4.6, and Codex . and the first version of this setup was a disaster. agents writing to the same files, redundant enrichment runs, opus doing grunt work that codex handles in a third of the cost. the routing wasn't a config problem. it was an architecture problem.

here's how the harness is built now.

---

**the model routing table**

every task type gets a model assignment before anything spawns. I keep this in a `router.yaml`:

```yaml
routing:
 explore_codebase: codex
 write_tests: codex
 refactor_logic: sonnet
 architecture_decision: opus
 review_output: opus
 write_draft_content: sonnet
 enrich_data: codex
 debug_failure: opus
```

simple key-value. the orchestrator reads this before spawning. no model picks its own assignment. that was the first thing I got wrong . letting the planning agent decide which model to use. it always picked opus because opus sounds capable. cost went sideways fast.

---

**the work queue with locks**

each task gets written to a SQLite queue before any agent touches it:

```sql
CREATE TABLE task_queue (
 id TEXT PRIMARY KEY,
 task_type TEXT,
 status TEXT DEFAULT 'pending', -- pending / claimed / done / failed
 assigned_model TEXT,
 created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
 claimed_at DATETIME,
 output_path TEXT
);
```

when an agent starts a task it flips status to `claimed` and writes its model ID. before any new task is spawned, the orchestrator runs:

```sql
SELECT task_type, status, assigned_model 
FROM task_queue 
WHERE status IN ('pending', 'claimed');
```

if a task_type is already claimed, it doesn't spawn a duplicate. this killed about 70% of the redundant work I was seeing.

---

**the review gate**

this is the one nobody builds until they get burned. autonomous agents will confidently produce wrong output. you need a gate that blocks the next stage until a review passes.

my gate is a simple python check that runs after every `done` task:

```python
def review_gate(task_id: str, reviewer_model: str = "opus") -> bool:
 task = db.get_task(task_id)
 output = read_file(task.output_path)
 
 prompt = f"""
 Review this output for task type: {task.task_type}
 
 Output:
 {output}
 
 Return JSON: {{"pass": true/false, "issues": []}}
 """
 
 result = call_model(reviewer_model, prompt)
 
 if not result["pass"]:
 db.update_status(task_id, "failed", notes=result["issues"])
 return False
 
 db.update_status(task_id, "done_reviewed")
 return True
```

opus reviews everything. codex and sonnet do not review their own work. that's the rule. the cost delta between having opus spot-check vs. having opus do the primary work is significant . and the quality gate catches the meaningful failures.

---

**the orchestrator loop**

the whole thing runs on a 30-second poll:

```python
while True:
 pending = db.get_pending_tasks()
 
 for task in pending:
 model = router[task.task_type]
 spawn_agent(task, model)
 
 done_unreviewed = db.get_done_unreviewed()
 
 for task in done_unreviewed:
 review_gate(task.id)
 
 time.sleep(30)
```

nothing fancy. the discipline is in the queue and the router, not the loop.

---

### REDDIT Version

spawning 10 agents is not the flex. getting autonomous useful output is the unsolved problem.

everyone figured out orchestration. subagents, parallel runs, fan-out patterns . the tooling got good, the tutorials are everywhere, the repos are clean. that part is solved.

the part nobody talks about: how do you know the agent actually did the thing?

I'm not being rhetorical. I mean this literally. an agent that writes "I successfully updated 47 files" is not evidence that 47 files were updated correctly. it's a confident sentence. those are not the same thing.

I've been burned by this exact pattern more times than I want to count. agent completes a task, summary looks clean, I move on. two days later something's broken and I trace it back to a subtask that hallucinated its output and reported success anyway.

the review layer is where most multi-agent setups are invisible and incomplete:

- you ask the agent if it worked, and it says yes
- you ask the orchestrator if the subagent worked, and it says yes (because the subagent said yes)
- nobody went back to the source of truth

what actually works, at least for me:

**deterministic verification over agent confirmation.** if the agent was supposed to write a file, check the file exists and has content. if it was supposed to call an API, check the response code is in your logs. if it was supposed to update a db row, query the row. trust the artifact, not the summary.

**structured output that includes evidence, not just status.** instead of `{ "status": "complete" }`, require `{ "status": "complete", "rows_affected": 14, "sample_output": [...] }`. you still might get hallucinated evidence, but at least you've built a surface to verify against.

**a separate reviewer agent that doesn't share context with the worker.** this one's expensive but it catches stuff. fresh context, no memory of what the worker "intended" to do, just look at what's actually there and judge it.

**explicit failure modes written into the prompt.** tell the agent: "if you cannot verify X, return status: blocked, not status: complete." agents default to optimism. you have to instruct pessimism.

the real trap is that multi-agent workflows feel productive. lots of tokens, lots of tool calls, clean summaries in the terminal. it looks like output. sometimes it is. sometimes you've built a very confident, very fast hallucination pipeline and you won't find out until it matters.

orchestration is a distribution problem. verification is a trust problem. we solved distribution in 2024. trust is still 2025's unsolved thing.
