### REDDIT Version

how I run Claude Code 24/7 without hitting limits (the actual setup)

most people ask this as a terminal question. it's actually an architecture question.

leaving a session open doesn't work. you hit the context limit, the session dies, you lose state. if you've got an agent mid-task, it's gone. this is the wrong mental model.

here's what actually works:

---

**the three pieces you need**

**1. a task datastore**

your agent needs external memory. not in the conversation, in a file or db it can read/write between sessions.

I use SQLite. dead simple schema:

```sql
CREATE TABLE tasks (
 id INTEGER PRIMARY KEY,
 status TEXT, -- pending / in_progress / done / failed
 description TEXT,
 context TEXT, -- any state the agent needs to resume
 updated_at TEXT
);
```

every task lives here. when a session ends, nothing is lost. the next session reads the table and picks up where it left off.

**2. an orchestrator session**

this is the session you don't do work in. it only does one thing: check the task table and spawn the right worker session.

```bash
# orchestrator loop (simplified)
while true; do
 next_task=$(sqlite3 tasks.db "SELECT id, description FROM tasks WHERE status='pending' LIMIT 1")
 if [ -n "$next_task" ]; then
 claude -p "resume task: $next_task. update status to done when finished." --output-format stream-json
 fi
 sleep 30
done
```

the orchestrator session is lightweight. it has no context from the work itself, so it almost never hits limits.

**3. limit-aware cycling**

the worker sessions do the actual work. each one:
- reads its task from the db
- does the work
- writes output + updated status back to the db
- exits

you don't try to keep one session alive forever. you cycle intentionally. each session starts fresh with only what the task row tells it to know.

---

**the flow end to end**

```
orchestrator (always on)
 → reads pending tasks from SQLite
 → spawns worker: claude -p "do task X, context: [row data]"
 → worker completes, writes to db, exits
 → orchestrator picks up next task
 → repeat
```

---

**a few things that actually matter**

write context aggressively into the task row. don't assume the next session remembers anything. file paths, partial outputs, decisions made, all of it goes in `context`.

mark tasks `in_progress` before starting. if the session crashes, your orchestrator can detect stale `in_progress` rows (older than N minutes) and reset them to `pending`.

```sql
UPDATE tasks 
SET status='pending' 
WHERE status='in_progress' 
AND updated_at < datetime('now', '-10 minutes');
```

keep worker prompts short and specific. the bigger the system prompt, the faster you burn context. worker sessions should have one job.

---

**what this solves**

- context limits: each worker is short-lived by design, never approaches the ceiling
- session crashes: state is in db, not in memory
- parallel work: you can run multiple workers on independent tasks simultaneously
- resumability: any task can restart cleanly from its last written state

the orchestrator pattern is just queue + worker. you've seen it before. the only difference is Claude Code is your worker runtime.

---

happy to share the full orchestrator script if useful. runs on a $5 Railway instance, been up for weeks.

**Target sub:** r/r/ClaudeCode

### REDDIT Version

the CLAUDE.md rules I keep in every project (and what each one actually fixes)

---

after 50+ projects I've stopped thinking of CLAUDE.md as "instructions for Claude." it's the guardrail layer. the thing that makes it safe to walk away from a terminal session and come back to work that didn't break something it wasn't supposed to touch.

here's the standing ruleset I've converged on, and the problem each rule was written to solve.

---

**never delete files without confirming first**

fixes: the agent deciding that a "cleanup" task means removing files it can't trace to an import. lost two hours of work once before this became permanent.

```
NEVER delete files without explicit user confirmation. 
If cleanup is needed, list what you'd delete and wait for approval.
```

---

**no silent fallbacks**

fixes: the agent hitting an error, swallowing it, substituting a default, and giving you output that looks correct but isn't. you only find out three steps later when something downstream breaks.

```
Do not use silent fallbacks. If a value is missing or an API call fails, 
stop and report the error. Do not substitute defaults without telling me.
```

---

**read before you write**

fixes: the agent generating a new version of a file it's never actually read, overwriting working logic because it inferred what was probably there.

```
Before editing any file, read it first. 
Do not infer file contents from file names or surrounding context alone.
```

---

**one task at a time, then stop**

fixes: task drift. you ask Claude to fix a bug and it also refactors three functions, renames variables it found confusing, and restructures a module. each change is "reasonable." none of them were asked for.

```
Complete the specific task requested, then stop. 
Do not refactor, rename, or restructure anything not directly related to the task.
```

---

**no assumed environment**

fixes: the agent hardcoding paths, assuming a specific Python version, or calling a CLI tool that exists on your machine but not in prod. especially painful in Railway deploys.

```
Do not assume the execution environment. 
Ask before hardcoding paths, versions, or CLI dependencies not listed in requirements.
```

---

**schema changes require a checkpoint**

fixes: the agent altering a SQLite schema mid-session and breaking every downstream query. database changes need to be atomic and intentional.

```
Treat all database schema changes as irreversible. 
List the change, confirm before executing. Never migrate inline without review.
```

---

**no credentials in output**

fixes: obvious. but Claude will helpfully paste an API key into a code block if you ask it to "show me the full config." this rule makes it refuse.

```
Never include API keys, tokens, passwords, or secrets in any output, 
code block, or file write. Reference env vars by name only.
```

---

**if you're stuck, say so**

fixes: the agent looping. generating variation after variation of the same broken approach instead of stopping and surfacing the blocker. you come back to 40 failed attempts instead of one honest "I'm blocked."

```
If you've attempted the same approach twice without success, stop. 
Describe what you tried and what the blocker is. Do not retry the same pattern.
```

---

**ask before installing packages**

fixes: dependency creep. the agent adding a library to solve a three-line problem you could have handled with stdlib. especially bad when you're in a locked environment.

```
Do not install packages or add dependencies without listing them 
and confirming first. Prefer stdlib solutions where viable.
```

---

**log what you changed**

fixes: sessions where you weren't watching the terminal and come back to a repo that's different but you don't know where. this one's underrated.

```
After completing any task that modifies files, output a summary of: 
what files were changed, what was changed, and why.
```

---

the meta-pattern across all of these: they're not about making Claude smarter. they're about making the failure modes legible. when something goes wrong, I want it to fail loudly and stop, not silently continue and make the problem worse.

most CLAUDE.md files I see are just vibes. "be concise. be helpful." that's fine for chat. it doesn't hold up when you're running a 40-step data pipeline at 2am and nobody's watching the terminal.

the guardrail layer is what makes autonomous work actually autonomous.
