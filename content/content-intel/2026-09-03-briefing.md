### REDDIT Version

fable 5.1 as orchestrator, opus/sonnet as the hands: the tier separation that actually fixes your quota burn

took me longer than I want to admit to figure this out. I kept pointing fable directly at tasks and watching my quota disappear. wrong mental model entirely.

here's what actually works:

**the architecture**

fable 5.1 handles the thinking layer. it reads the codebase, maps dependencies, writes the plan, decides the execution order. it never touches a file. opus or sonnet gets handed that plan and does the actual work: edits, writes, runs bash, checks outputs.

in claude.md or your system prompt, you define this explicitly:

```
orchestrator: claude-fable-5-1
executor: claude-opus-4-6

orchestrator role: planning, decomposition, review
executor role: file edits, bash, tool calls
```

then in your agent loop, fable produces a structured task list before any tool call happens. something like:

```python
orchestrator_prompt = """
analyze this codebase and produce a numbered task list.
each task: what file, what change, what the success condition is.
output only the plan. do not call any tools.
"""

plan = fable.complete(orchestrator_prompt)
executor.run(plan) # opus/sonnet from here
```

**why the quota math changes**

fable tokens are priced differently and the thinking depth is where it earns its cost. but the expensive part of most sessions isn't the planning. it's the repeated file reads, the tool calls, the bash loops. that's all executor territory.

when fable is doing executor work too, you're paying fable rates for tasks that sonnet handles just as well. separating the tiers means fable usage stays flat (one planning pass per feature), executor usage scales with actual work volume but at lower cost.

on a 10-file refactor I was watching fable tokens stack up on every intermediate step. after the split: fable does one planning pass, sonnet runs the 40+ tool calls. quota impact dropped roughly 60% on the executor side.

**the pattern that makes it stick**

fable reviews the output too. after sonnet finishes a block, pass the diff back to fable for a critique pass before moving to the next task. fable at review is cheap because it's reading, not executing. you get the model quality on planning and review without paying for it on every file write.

```
fable: plan
sonnet: execute block 1
fable: review block 1, approve or revise plan
sonnet: execute block 2
...
```

**what to watch for**

context bleed is the main failure mode. if you let the executor's full conversation history feed back into fable, you're compressing the orchestrator's working memory with noise it didn't need. keep them in separate context windows. pass structured summaries between them, not raw transcripts.

also: fable doesn't always know when it should just let sonnet make a judgment call. build an explicit handoff condition in your orchestrator prompt. "if you encounter an ambiguity that requires a file read to resolve, flag it and stop. do not attempt to infer." otherwise fable hallucinates file contents it hasn't seen and the plan breaks immediately.

anyone else running a tiered setup like this? curious what orchestration patterns are actually holding up at scale.

## 8. [RESOURCE_SHARE] why I replaced every .md context file with SQLite columns

**Thesis:** Agent memory in .md files works fine until your project grows. SQLite columns let you query context instead of dump it, which means the agent sees exactly what's relevant rather than reading the entire history every session.
**Target sub:** r/r/ClaudeCode
**Scores:** viral=7 voice=10 gap=8 effort=medium

### REDDIT Version

why I replaced every .md context file with SQLite columns

been using Claude Code for a few months and the context management pattern everyone starts with is the same: a bunch of .md files. CLAUDE.md, context.md, decisions.md, notes.md. works great at the start.

then your project grows.

I hit the wall around project week 6. CLAUDE.md was 800 lines. decisions.md had contradictions in it from different sessions. the agent was reading the whole thing every time and still surfacing the wrong context because the relevant decision was buried under 40 other ones.

the fix was obvious in hindsight: stop dumping context, start querying it.

here's the schema I settled on:

```sql
CREATE TABLE context (
 id INTEGER PRIMARY KEY,
 scope TEXT, -- 'project' | 'file' | 'decision' | 'pattern'
 key TEXT,
 value TEXT,
 tags TEXT, -- comma-separated
 created_at TEXT,
 updated_at TEXT
);
```

now instead of reading the whole file, I run a query at the start of any session:

```python
def get_context(scope=None, tags=None):
 query = "SELECT key, value FROM context WHERE 1=1"
 if scope:
 query += f" AND scope = '{scope}'"
 if tags:
 tag_conditions = " OR ".join([f"tags LIKE '%{t}%'" for t in tags])
 query += f" AND ({tag_conditions})"
 return conn.execute(query).fetchall()
```

I pipe the output into the Claude Code session context. the agent gets exactly what's relevant to the task, not the entire history of every decision I've ever made.

a few things this unlocked:

**scoped context per file**: I tag rows with the file path. when I'm working on `enrichment/apollo.py`, the agent sees the decisions and patterns specific to that module. nothing else.

**decision history with timestamps**: .md files have no memory of when something was decided. SQLite does. I can query "what changed in the last 7 days" and hand the agent a change log instead of the whole doc.

**agent writes back**: the agent can INSERT new rows during a session. when it makes a significant architectural decision, I have it log that to the context table. next session it's there. no more "wait didn't we decide this already" moments.

**grep across context**: `SELECT * FROM context WHERE value LIKE '%rate limit%'` beats manually scanning five .md files.

the migration was one afternoon. I wrote a script to parse my existing .md files and seed the table. not perfect, but good enough to start querying.

if you're hitting the 800-line CLAUDE.md wall, this is the next step. .md files are a great v1. SQL is v2.

happy to share the full migration script if useful.
