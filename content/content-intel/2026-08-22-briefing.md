how to build agent checkpoints that prevent your subagent from nuking production (here's the actual architecture)

lost a staging database last month. subagent was cleaning up "stale" records and decided 90% of the table qualified. technically correct. catastrophically wrong. took four hours to restore.

that's not a model problem. that's a process design problem. the agent had no checkpoint between "plan the action" and "execute the action." i gave it the wheel and walked away.

here's the checkpoint schema I've been running since then. zero production incidents.

---

**the core problem**

most agentic loops look like this:

```
task → plan → execute → done
```

the gap is between plan and execute. that's where irreversible actions happen with no human gate. the fix isn't making the agent smarter . it's making the *process* require approval before anything destructive runs.

---

**the checkpoint table**

```sql
CREATE TABLE agent_checkpoints (
 id TEXT PRIMARY KEY,
 task_id TEXT NOT NULL,
 action_type TEXT NOT NULL, -- 'read' | 'write' | 'delete' | 'external'
 reversible INTEGER NOT NULL, -- 0 or 1
 blast_radius TEXT NOT NULL, -- 'row' | 'table' | 'service' | 'infra'
 payload JSON NOT NULL, -- full action params
 status TEXT DEFAULT 'pending', -- 'pending' | 'approved' | 'rejected' | 'executed'
 created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
 reviewed_at DATETIME,
 reviewed_by TEXT -- 'human' | 'auto' (for safe ops)
);
```

every action the agent plans gets written here before anything executes. the agent cannot skip this step . it's baked into the tool definition.

---

**the tool wrapper**

instead of giving your subagent direct db access, wrap every mutation in a checkpoint gate:

```python
def agent_action(action_type, payload, reversible=True, blast_radius="row"):
 checkpoint_id = str(uuid.uuid4())
 
 db.execute("""
 INSERT INTO agent_checkpoints 
 (id, task_id, action_type, reversible, blast_radius, payload)
 VALUES (?, ?, ?, ?, ?, ?)
 """, [checkpoint_id, current_task_id, action_type, 
 int(reversible), blast_radius, json.dumps(payload)])
 
 # auto-approve safe ops
 if reversible and blast_radius == "row":
 db.execute("UPDATE agent_checkpoints SET status='approved', reviewed_by='auto' WHERE id=?", [checkpoint_id])
 return execute_action(payload)
 
 # everything else waits
 return {"status": "checkpoint_created", "id": checkpoint_id, "requires_approval": True}
```

the agent gets back a checkpoint ID and stops. it cannot proceed until that checkpoint is approved. you review it, you approve it, then the agent calls `execute_checkpoint(id)`.

---

**the classification rules**

this is the part most people skip and then wonder why they're in the auto-approve loop for everything:

| action | reversible | blast_radius | auto-approve? |
|---|---|---|---|
| SELECT query | yes | row | yes |
| INSERT single row | yes (can delete) | row | yes |
| UPDATE with WHERE | depends | row/table | check row count first |
| DELETE with WHERE | no | row/table | **no** |
| DROP / TRUNCATE | no | table | **no** |
| API call (write) | no | service | **no** |
| File delete | no | infra | **no** |

the key insight: *row count matters more than action type.* an UPDATE touching 50,000 rows is not the same as an UPDATE touching 3 rows. add a pre-flight row count check before classifying blast_radius.

```python
def classify_blast_radius(action_type, table, where_clause):
 if action_type in ("DELETE", "UPDATE", "TRUNCATE"):
 count = db.execute(f"SELECT COUNT(*) FROM {table} WHERE {where_clause}").fetchone()[0]
 if count > 1000:
 return "table", False # blast_radius, reversible
 elif count > 1:
 return "row", False
 return "row", True
```

---

**the approval flow**

i run a dead simple CLI loop that polls pending checkpoints:

```python
def review_pending():
 pending = db.execute("""
 SELECT id, action_type, blast_radius, payload 
 FROM agent_checkpoints 
 WHERE status = 'pending'
 ORDER BY created_at
 """).fetchall()
 
 for checkpoint in pending:
 print(f"\n[{checkpoint['action_type']}] blast: {checkpoint['blast_radius']}")
 print(json.dumps(json.loads(checkpoint['payload']), indent=2))
 decision = input("approve? (y/n): ").strip().lower()
 
 status = "approved" if decision == "y" else "rejected"
 db.execute("""
 UPDATE agent_checkpoints 
 SET status=?, reviewed_at=CURRENT_TIMESTAMP, reviewed_by='human'
 WHERE id=?
 """, [status, checkpoint['id']])
```

not pretty. works perfectly. i run this in a second terminal tab while the agent works. takes about 10 seconds per checkpoint review. every production-touching action gets a human eye.

---

**what changed after adding this**

the staging incident would have been caught at the blast_radius classification step. `DELETE WHERE created_at < ?` on a table with 40k rows → blast_radius="table", reversible=False, auto-approve=no. I see it, I see the row count, I reject it and reprompt with better constraints.

the agent didn't need to be smarter. it needed a process that made the destructive action visible before execution, not after.

---

**one more thing**

add a dry-run mode to every destructive tool. before any DELETE or UPDATE, have the agent run:

```python
def dry_run(action_type, table, where_clause):
 count = db.execute(f"SELECT COUNT(*) FROM {table} WHERE {where_clause}").fetchone()[0]
 sample = db.execute(f"SELECT * FROM {table} WHERE {where_clause} LIMIT 5").fetchall()
 return {"would_affect": count, "sample": sample}
```

the agent shows you what it's about to do. you confirm or redirect. it's two extra lines in the tool and it's caught me from fat-fingering WHERE clauses three times since I added it.

---

the mental model: agents are fast and they don't feel regret. you are slow and you do. build the process so your speed matches the decision weight. irreversible actions should always be slow.

what I do before any agent gets write access to anything that matters:

**1. define the blast radius first**

before I wire up an agent to anything, I ask: what's the worst single action this agent can take? if the answer is "delete a table" or "fire 500 emails" or "execute a trade", that action needs a confirmation gate. not a prompt like "are you sure?" . a hard interrupt that requires deliberate human input before continuing.

**2. dry-run mode as default**

if your agent only needs to read from a database, it only gets read credentials. if it needs to write to one table, it doesn't get write access to five. principle of least privilege isn't just a security concept . it's an agent design pattern.

**4. log before you act**

every write action gets logged to a local file before execution. this costs nothing and gives you a paper trail if something goes sideways. I pipe it to a SQLite table so I can query what the agent did and when.

**5. the irreversibility test**

I split every agent action into two buckets: reversible and irreversible. reversible actions (draft an email, generate a report, update a staging table) can run autonomously. irreversible actions (send the email, drop the table, execute the trade, push to prod) always need a gate.

the model doesn't know what's irreversible in your context. you do. that's the whole job.

people are shipping faster than ever with agents. that's genuinely good. but the failure mode isn't "agents are too powerful" . it's "builders are wiring agents to live systems before they've built the safety layer."

create the rails before you build the features. the rails aren't slowing you down. they're what makes it safe to go fast.
