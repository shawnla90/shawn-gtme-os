## 1. [TUTORIAL] the CLAUDE.md rules that actually constrain agent behavior (with the exact syntax)

**Thesis:** Most CLAUDE.md files are vague vibes that don't change what the agent does. The rules that actually fire are constraint-based with explicit failure modes — here's the difference and the patterns that work.
**Target sub:** r/r/ClaudeCode
**Scores:** viral=8 voice=9 gap=7 effort=medium

### REDDIT Version

most CLAUDE.md files are aspirational. "be concise", "prefer functional patterns", "don't over-engineer". the agent reads them, acknowledges them, and then does whatever it was going to do anyway.

I spent a couple weeks debugging this. here's what I found: vague preferences barely register. constraint-based rules with explicit failure modes actually fire.

the difference in practice:

**vague (doesn't stick):**
```
- Be concise in your responses
- Prefer simple solutions
- Don't add unnecessary comments
```

**constraint (actually fires):**
```
- NEVER create a file unless explicitly asked. If you think a new file is needed, say so and stop.
- Do NOT run git push without user confirmation. Period.
- If a test fails, do not retry the same command more than once. Stop and explain.
```

five patterns I've found that actually work:

1. **NEVER/DO NOT beats prefer/avoid** . strong negation loads differently than preference language. the model treats NEVER as a hard stop, not a nudge.

2. **tie the rule to an action, not a quality** . "don't over-engineer" is a quality judgment the model has to interpret. "don't create helper functions for one-time operations" is an action it can check against.

3. **add what to do instead** . "don't retry failing tests. stop and explain what you tried and what the error was." without the redirect, the agent sometimes halts awkwardly with nothing to offer.

4. **name the failure mode explicitly** . "if you run rm -rf, the user will lose work permanently. confirm before any destructive command." consequence framing appears to activate different behavior than preference framing. I don't know exactly why, but the pattern holds.

5. **scope your rules precisely** . "NEVER auto-push" fires on every git operation including branches you want it to touch. "NEVER push to main without confirmation" is more surgical.

here's a chunk from my actual CLAUDE.md I've stress-tested across a few hundred sessions:

```markdown
# Execution guardrails

- NEVER run destructive commands (rm -rf, DROP TABLE, git reset --hard, force push) 
 without explicit confirmation in this message. Stopping to ask is not blocking progress.
- Do NOT create files to solve problems that editing an existing file would solve. 
 If you think you need a new file, say why before creating it.
- If a bash command fails, do not retry it silently. Stop, show the error, explain 
 what you're trying differently.
- NEVER write to .env files. Read if needed, never write.
- Do not add error handling for scenarios that cannot happen inside this codebase. 
 Only validate at system boundaries (user input, external APIs).
```

the last one is still the hardest to enforce. "don't add error handling for scenarios that can't happen" gets interpreted loosely almost every session. still tuning it. if you have a version that sticks, drop it in the comments.

one more thing: rule density matters. I tested files with 40+ rules and they start to conflict and cancel each other out. I now keep my root CLAUDE.md under 30 actionable lines and push project-specific rules into CLAUDE.md files scoped to subdirectories. the local file wins on scope, which is actually useful once you learn to use it deliberately.

## 7. [PSA] PSA: if you're using Claude Code via API, check your token billing before your next invoice

That number is not a typo.

here's what's happening:

**the compounding loop nobody explains**

Every turn in a long Claude Code session re-sends the context. With prompt caching on, those re-sends are "cache reads" . billed at 10% of normal input cost. Sounds cheap. But:

- your CLAUDE.md gets injected every turn
- tool results get appended to the conversation history
- each sub-agent spawns with a full copy of the system prompt
- a 3-hour session with 200+ turns, each reading 100k+ tokens = 20M+ cache read tokens
- if you're running sub-agents in parallel, multiply that by however many you spawned

cache reads are cheap per token. but they are not free. and they compound across a long session in ways the token counter in your terminal doesn't show you.

**where to actually check**

go to console.anthropic.com → usage → toggle to "tokens" view, not just cost. filter by model. you'll see:

- input tokens (what you think you're spending)
- cache write tokens (one-time, when context gets cached)
- cache read tokens (the one that gets spicy)
- output tokens

the ratio of cache reads to actual input is where most people get surprised.

**what actually helps**

1. `/compact` aggressively. don't let sessions run 200 turns with a growing context. compact at natural breakpoints.

2. keep CLAUDE.md lean. every byte in that file gets re-injected constantly. if yours is 8k tokens, that's 8k tokens × every turn × every sub-agent. trim it.

3. set a `--max-turns` flag when you know a task is bounded. sub-agents especially.

4. check the usage page weekly if you're doing any heavy API work. daily if you're running long overnight sessions.

the subscription ($100/month) sidesteps all of this . it's metered on Anthropic's side and you just hit rate limits instead of a bill. but if you're on API-direct for workflow reasons, this stuff sneaks up on you fast.
