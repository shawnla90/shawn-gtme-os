the problem with relying on a single model: you hit the rate limit right when you're in flow. you wait. the context cools. you lose the thread.

the worse problem: you trust one model's output because you have nothing to compare it against.

I fixed both by running Claude Code in terminal and Codex in the Windsurf/VS Code app at the same time, treating them as adversarial reviewers of each other's work.

**the setup**

Claude Code: terminal, full agentic mode, handles the heavy builds. I give it a task, it runs tools, edits files, runs tests, iterates. I'm doing other things while it works.

Codex: running in the app sidebar with access to the same repo. its job is to review what Claude Code just produced.

they share the same file system. they don't share rate limits.

**the actual workflow**

1. give Claude Code the build task. full context, clear scope. let it run.

2. while it's working, I'm in Codex setting up the review prompt. something like:

```
review the changes in [file]. 
look for: logic errors, edge cases not handled, security issues, places where the implementation doesn't match the original intent.
be adversarial. your job is to find what's wrong, not validate what's right.
```

3. Claude Code finishes. I paste the diff or the relevant file into Codex.

4. Codex comes back with a critique. sometimes it's "looks solid." more often it catches something: a variable name that shadows an outer scope, a missing null check, a case where the logic works for the happy path but breaks on empty input.

5. I take the critique back to Claude Code: "Codex flagged X and Y. address these before we move on."

6. Claude Code iterates. I send the revision back to Codex for a second pass.

**why this works**

models have different training distributions and different failure modes. Claude Code will confidently do something Codex would never do, and vice versa. the disagreements are the signal.

it's not about one being smarter. it's about two different systems looking at the same output. the adversarial dynamic forces justification . when Claude Code has to fix what Codex flagged, it produces tighter code than it would have on the first pass.

and the throughput thing: while Codex is reviewing, Claude Code is already idle and ready for the next task. or I've queued a parallel task. the wait time that used to kill my flow is now the review window.

**the rate limit angle**

Claude Code and Codex pull from completely separate rate limit pools. if you hammer Claude Code until it's throttled, Codex is completely unaffected and vice versa. in practice I almost never hit limits anymore because the review cycle naturally spaces out the heavy requests.

**what I actually use this for**

- any build over 200 lines of changed code gets a Codex review pass before I commit
- schema changes always go through both (caught a FK constraint issue last week that would have been a production migration nightmare)
- prompt engineering: Claude Code writes the prompt, Codex red-teams it for injection vectors and edge cases

**what doesn't work**

don't use this for back-and-forth conversation. the context switching overhead kills the value. it's for discrete build → review → iterate loops, not streaming collaboration.

also: they'll sometimes disagree and both be wrong in different directions. you still have to read the output. these are reviewers, not oracles.

---

the setup takes about 10 minutes to configure once. after that it's just a habit: build in one, review in the other, never sit idle waiting for a limit to clear.

happy to share the review prompt templates I use most if anyone wants them.

## 7. [PSA] someone is pentesting AI-built apps for free and the findings are alarming — here's what to actually check before you ship

### REDDIT Version

someone is pentesting AI-built apps for free and the findings are alarming . here's what to actually check before you ship

been seeing a pattern in the wild: security researchers are specifically targeting vibe-coded apps because they know the common failure modes. and honestly? the findings are rough.

here's what's showing up over and over.

**IDOR everywhere**

insecure direct object references. you built an endpoint like `/api/users/123/data` and the only thing protecting user 124's data is... the user not knowing to change the number.

```
# what AI generates (bad)
@app.get("/api/orders/{order_id}")
async def get_order(order_id: int, current_user = Depends(get_current_user)):
 return db.query(Order).filter(Order.id == order_id).first()

# what you actually need
@app.get("/api/orders/{order_id}")
async def get_order(order_id: int, current_user = Depends(get_current_user)):
 order = db.query(Order).filter(
 Order.id == order_id,
 Order.user_id == current_user.id # <- this line is the whole game
 ).first()
 if not order:
 raise HTTPException(status_code=404)
 return order
```

AI builds the happy path. it does not build paranoid authorization by default.

**unauthenticated admin routes**

the LLM creates `/admin/users`, adds it to the router, and never wires up the auth middleware because you didn't ask for it. it's live. it works. it has no protection.

check: grep your codebase for every route definition and verify each one has an auth dependency or is explicitly public by design.

```bash
# quick audit . find every route missing auth
grep -n "@app\.\(get\|post\|put\|delete\)" your_app.py | grep -v "Depends"
```

that list should be very short. if it's long, you have work to do.

**exposed .env values in client bundles**

next.js and similar frameworks have a `NEXT_PUBLIC_` prefix convention for a reason. if you have `NEXT_PUBLIC_STRIPE_SECRET_KEY` in your env, that key is in the browser bundle. this is not a hypothetical . it's happened on shipped products.

also: any API route that does `return {"debug": os.environ}` for troubleshooting and never got removed.

**rate limiting on auth endpoints**

`/api/login` with no rate limiting is a brute force welcome mat. AI doesn't add this unless you ask. same for `/api/forgot-password`.

```python
from slowapi import Limiter
from slowapi.util import get_remote_address

limiter = Limiter(key_func=get_remote_address)

@app.post("/api/login")
@limiter.limit("5/minute")
async def login(request: Request, credentials: LoginRequest):
 ...
```

**the checklist before you ship to real users**

1. every authenticated route: does it verify the resource belongs to the requesting user, not just that the user is logged in?
2. grep for routes without auth middleware . every hit needs a reason
3. audit your env vars: anything in the client bundle that shouldn't be?
4. test `/admin/*` routes as a non-admin user . do they 401?
5. check your file upload endpoints: does it validate file type server-side, not just client-side?
6. rate limit on: login, password reset, OTP verification, any endpoint that triggers an email/SMS
7. does your error response leak stack traces or internal paths in production?

the vibe coding workflow is incredible for shipping fast. the gap is that LLMs optimize for "working" not "secure by default." adding security isn't anti-vibe . it's just a second pass you have to build into the habit.

run your own app through [OWASP's testing guide](https://owasp.org/www-project-web-security-testing-guide/) top 10 before someone else does it for you.

I keep seeing people reach for Fable the moment they want parallelism. I get it. The pitch is seductive: 10 subagents spinning up, each one handling a slice of your build, all coordinated automatically.

then you're at midnight debugging a cascading loop where agent 4 handed bad output to agent 7 which poisoned agent 9's context and now you can't tell where the corruption started.

here's what actually works for most builds:

Claude Code in the terminal as the orchestrator. Codex in the app as the reviewer. two agents. one context boundary. you stay in control of the handoff.

the workflow I run:

Claude Code builds the thing . script, schema change, enrichment logic, whatever. when it's done, I paste the output into Codex with a single prompt: "what breaks here, what did it miss, what would you do differently." that's your parallelism. two models, different training, different priors, different blind spots. you get real coverage without a coordination layer you have to babysit.

the reason Fable-style orchestration gets messy is the same reason microservices get messy: every boundary is a failure surface. more agents means more contracts, more failure modes, more places where a bad assumption propagates before you catch it.

for 90% of builds . enrichment scripts, outreach tooling, data pipeline work, CRM sync . the two-agent pattern is enough. you ship faster because you're not setting up the orchestration scaffolding, you're not writing the agent communication layer, and when something breaks you know exactly where to look.

the 10% where Fable makes sense: genuinely parallel workstreams that don't share state, long-running research tasks where you want true async, situations where you've already hit the two-agent ceiling and you know it because you tried it first.

reach for complexity when the simple version actually fails you. not before.
