---

**the core idea**

not all tasks have the same complexity ceiling. the mistake is treating model selection as a quality setting (more expensive = better output) when it's actually a match problem. a JSON extraction task doesn't need Opus any more than you need a surgeon to take your blood pressure.

the three buckets:

- **Haiku**: lookup, classification, extraction, boolean decisions, format checks, anything where the answer space is constrained
- **Sonnet**: drafting, summarization, code gen for known patterns, moderate reasoning, anything where you need fluency but not deep synthesis
- **Opus**: multi-step planning under ambiguity, reasoning across long or conflicting context, anything where the model needs to hold contradictions and resolve them

---

**the router**

I use a lightweight classifier . ironically, Haiku itself . to categorize the incoming task before it routes. the classifier prompt is short:

```
Given this task description, return one of: [lookup, draft, reason]

Rules:
- lookup: extracting, classifying, formatting, yes/no, list retrieval
- draft: writing, summarizing, generating familiar code patterns
- reason: planning, debugging complex state, synthesis across conflicting sources

Task: {task}
Return only the label.
```

that call is ~100 tokens total. cheap insurance.

```python

 response = client.messages.create(
 model="claude-haiku-4-5-20251001",
 max_tokens=10,
 messages=[{"role": "user", "content": ROUTER_PROMPT.format(task=task)}]
 )
 return response.content[0].text.strip()

def route(task: str, context: str) -> str:

 "lookup": "claude-haiku-4-5-20251001",
 "draft": "claude-sonnet-4-6",
 "reason": "claude-opus-4-6",

 model=model,
 max_tokens=2048,

 return response.content[0].text
```

---

not dumb in a bad way. dumb in the "this was sitting right there and I was brute-forcing it" way.

quick context on how I was working before: I'd give Claude Code a task, it would edit files, and then I'd manually run my linter, run my tests, check formatting, notice something broke, go back and tell it, repeat. every session had this cleanup tail that I was doing myself.

turns out that tail is exactly what hooks are for.

---

**what hooks actually are**

hooks are shell commands that Claude Code runs automatically in response to events. not "Claude runs code in its context" . your shell runs code. that distinction matters because it's real system-level enforcement, not just vibes in the prompt.

the two I use most:

`PostToolUse` . fires after Claude uses a tool (file edit, bash command, etc.)
`PreToolUse` . fires before Claude uses a tool, can block the action entirely

you configure them in your `~/.claude/settings.json` under a `hooks` key.

---

**the exact hooks I run**

format on every file write:

```json
{
 "hooks": {
 "PostToolUse": [
 {
 "matcher": "Write|Edit",
 "hooks": [
 {
 "type": "command",
 "command": "cd $CLAUDE_PROJECT_DIR && npx prettier --write $CLAUDE_TOOL_INPUT_FILE_PATH 2>/dev/null || true"
 }
 ]
 }
 ]
 }
}
```

this means Claude can write sloppy formatting and it doesn't matter. the file that lands on disk is always clean. I stopped telling it "make sure to format correctly" entirely.

lint + test after bash runs that touch src:

```json
{
 "matcher": "Bash",
 "hooks": [
 {
 "type": "command",
 "command": "cd $CLAUDE_PROJECT_DIR && npm run lint --silent 2>&1 | tail -5"
 }
 ]
}
```

I pipe the last 5 lines back so if something breaks, Claude sees it immediately in the next tool result. it self-corrects without me having to say anything.

block force-push (the one that saved me):

```json
{
 "hooks": {
 "PreToolUse": [
 {
 "matcher": "Bash",
 "hooks": [
 {
 "type": "command",
 "command": "if echo \"$CLAUDE_TOOL_INPUT_COMMAND\" | grep -q 'git push --force'; then echo 'blocked: force push requires explicit approval'; exit 1; fi"
 }
 ]
 }
 ]
 }
}
```

exit code 1 from a PreToolUse hook blocks the action entirely and surfaces the message to Claude. so now "push the changes" never silently becomes "force push the changes" because the agent decided it needed to.

---

**the mental shift**

before hooks: I was treating Claude Code like a smart terminal user I had to supervise.

after hooks: I defined what "done" means at the system level, and now done means done.

the difference between "Claude Code doing what you meant" vs "Claude Code doing what you said" is mostly about whether you've encoded your invariants into the environment or left them floating in the prompt. prompts drift. hooks don't.

---

**env vars available inside hooks**

`$CLAUDE_PROJECT_DIR` . your project root 
`$CLAUDE_TOOL_NAME` . which tool fired 
`$CLAUDE_TOOL_INPUT_FILE_PATH` . the file path for write/edit operations 
`$CLAUDE_TOOL_INPUT_COMMAND` . the bash command string for Bash tool calls 

these make the hooks composable without hardcoding anything.
