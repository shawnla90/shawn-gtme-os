---

**section 1: project identity (5-10 lines max)**

this is NOT a readme. it's the model's operating context. one paragraph. answers: what does this project actually do, what's the primary data flow, what's the stack, and what's the non-obvious constraint the model will definitely hit.

example:
```
# project
clearbox reddit signal engine. reads intent from reddit comments via pushshift + reddit api, scores against icp, writes to sqlite. primary flow: scrape -> classify -> score -> export. constraint: reddit rate limits are aggressive . all api calls go through rate_limiter.py, never direct.
```

that last line saves me from watching the model rediscover the rate limiter every session.

---

**section 2: tool permissions (explicit, not implicit)**

most CLAUDE.md files say nothing about tools. then you spend 20 minutes watching the model hesitate on every bash call. be explicit:

```
# tools
- bash: approved for read ops, file edits, running tests. confirm before: pip install, git push, deleting files.
- write: approved. prefer edit over rewrite for existing files.
- glob/grep: approved, use before read when locating files.
- web fetch: approved for docs. not for search.
```

this isn't about restricting the model. it's about removing friction from the approved path so it moves fast on the stuff you want and pauses on the stuff you need to review.

---

**section 3: output rules**

the section most people skip. without it, style drifts over a long session:

```
# output rules
- functions: snake_case. classes: PascalCase. files: kebab-case.
- no type annotations unless explicitly requested.
- comments only where logic isn't self-evident.
- test files go in /tests/, mirror the source path.
- never rewrite a working function to "improve" it unless asked.
```

that last rule is the most important one I've ever added. the model loves to refactor things that are fine. this stops it.

---

**section 4: memory index (this is the one that actually scales)**

here's where it gets structural. anything beyond ~30 lines of context that the model needs to remember doesn't live in CLAUDE.md. it lives in sqlite. CLAUDE.md just holds the index:

```
# memory
persistent state lives in /memory/project.db

tables:
- decisions: architectural decisions with rationale and date (query when making changes to core structure)
- patterns: confirmed code patterns the project uses (query before generating new utilities)
- errors: recurring errors and their fixes (query at session start if hitting a known issue)

query memory when: starting a new feature, hitting an unexpected error, making changes to shared utilities.
write to memory when: a decision is made that will affect future sessions, a pattern is confirmed working.
```

then I have a memory.py helper that the model can call:

```python
import sqlite3, json
from datetime import datetime

def log_decision(db_path, decision, rationale, context=""):
 conn = sqlite3.connect(db_path)
 conn.execute("""
 INSERT INTO decisions (decision, rationale, context, created_at)
 VALUES (?, ?, ?, ?)
 """, (decision, rationale, context, datetime.now().isoformat()))
 conn.commit()
 conn.close()

def query_decisions(db_path, keyword):
 conn = sqlite3.connect(db_path)
 rows = conn.execute("""
 SELECT decision, rationale, created_at FROM decisions
 WHERE decision LIKE ? OR rationale LIKE ?
 ORDER BY created_at DESC LIMIT 5
 """, (f"%{keyword}%", f"%{keyword}%")).fetchall()
 conn.close()
 return rows
```

at session start I tell the model to query the decisions table before touching anything in the core flow. it takes 3 seconds and saves the "why is this structured this way" conversation.

---

**1. scoped tool lists per agent**

```python
DEDUP_AGENT_TOOLS = [

 "write_dedup_log"

]
```

the orchestrator only passes tools in that list. if the subagent tries to call something outside it, the wrapper raises before execution.

**2. write-once staging tables**

subagents never write to the live table. they write to a `_staging` shadow table. the orchestrator reviews the diff and promotes it with a manual confirm step . even in automated runs, the promotion requires an explicit `COMMIT_STAGING=true` env flag I set consciously before each run.

```sql

INSERT INTO contacts_staging SELECT ...

-- orchestrator promotes after diff review
INSERT INTO contacts SELECT * FROM contacts_staging WHERE reviewed = 1
```

if a subagent is in a loop, it needs an explicit done signal. I now require every looping subagent to return `{"status": "complete", "reason": "..."}` when it has nothing left to process. if it tries to start a new iteration without a pending work item, the orchestrator kills it. no wandering.

14. **posthog** . event queries for my product. Claude can pull funnel data, event counts, session breakdowns directly without me context-switching to the dashboard.
15. **redis** . job queue state. my enrichment workers push status here, Claude can read queue depth and job results without hitting the DB.
16. **puppeteer** . yeah I have both playwright and puppeteer wired. playwright handles most things. puppeteer stays because one specific scraping job breaks on playwright and I haven't traced why.
17. **exa** . semantic search over the web. I use this for research passes where keyword search fails. "find companies talking about X problem" type queries.

---

**the 3 I cut**

**zapier MCP** . looked useful on paper. "connect to 5000+ apps." in practice every operation was 3-4 tool calls deep, and half the time Claude would burn tokens trying to navigate the action schema before doing anything. I replaced it with direct API calls in my scripts. one python file, one job, no abstraction layer eating my context.

**linear** . I don't use Linear for solo builds. I added it thinking I'd route Claude toward issue tracking. never used it once. it just sat in the config adding surface area for token leakage on unrelated queries where Claude would try to "check if this is tracked" unprompted. cut it.

**everything-search (Windows desktop search)** . I was testing this during a setup on a different machine. it indexed way too broadly and Claude would pull completely unrelated file references when doing research tasks. the signal-to-noise ratio was terrible. if you're on Windows and want filesystem access, scope it explicitly. don't let it search everything.

---

**the config pattern that matters**

each server has explicit `args` with scoped paths or resource limits. I don't wire anything with broad permissions. filesystem gets two directories max. postgres gets read-only on tables I don't need agents writing to.

the other thing: I version my `claude_desktop_config.json` in the repo. when I add or remove a server, it's a commit. makes it easy to roll back when something starts acting weird after a change.
