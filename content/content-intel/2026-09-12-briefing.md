### REDDIT Version

how I run 100 parallel Claude Code sessions without losing my mind

**tl;dr**: spreadsheets and task lists fall apart past ~10 parallel agents. the fix is a private work graph in SQLite . sessions as nodes, dependencies as edges, blocking status as a live field. schema + query at the bottom, no gatekeeping.

---

I hit a wall around session 15.

I was running Claude Code in parallel across a monorepo . enrichment pipeline, email infra, analytics layer, frontend . and I genuinely could not tell you which session was blocked, which had already touched a shared file, or which two agents were about to write conflicting migrations.

Spreadsheet didn't cut it. By the time I updated it, it was wrong.

So I built a work graph. Here's the actual schema:

```sql
CREATE TABLE sessions (
 id TEXT PRIMARY KEY, -- e.g. "enrich-apollo-001"
 worktree TEXT NOT NULL, -- git worktree path
 goal TEXT NOT NULL, -- one-line intent
 status TEXT DEFAULT 'active', -- active | blocked | done | abandoned
 touches TEXT, -- JSON array of files/modules this session writes
 depends_on TEXT, -- JSON array of session IDs that must finish first
 blocker_note TEXT, -- plain text if status='blocked'
 started_at INTEGER,
 resolved_at INTEGER
);

CREATE TABLE session_log (
 id INTEGER PRIMARY KEY AUTOINCREMENT,
 session_id TEXT REFERENCES sessions(id),
 ts INTEGER DEFAULT (unixepoch()),
 event TEXT, -- 'started', 'blocked', 'checkpoint', 'done'
 note TEXT
);
```

the `touches` column is the one that saves you. before I spin up a new session I run:

```sql
SELECT id, goal, status
FROM sessions
WHERE status != 'done'
 AND json_each.value IN (SELECT json_each.value FROM json_each(?))
FROM sessions, json_each(sessions.touches)
WHERE sessions.status != 'done';
```

passing in the files I'm about to hand the new agent. if anything comes back, I either sequence it or scope the new session to avoid the conflict zone.

---

the dependency edge (`depends_on`) is what makes it a graph instead of a list. I insert edges when I know ordering matters . schema migration before data backfill, auth module before anything that needs a token. then one query gives me the ready set:

```sql
SELECT s.id, s.goal
FROM sessions s
WHERE s.status = 'active'
 AND NOT EXISTS (
 SELECT 1
 FROM sessions dep
 WHERE dep.id IN (SELECT value FROM json_each(s.depends_on))
 AND dep.status != 'done'
 );
```

anything in that result can run right now without blocking anything else. that's the queue I feed new terminals from.

---

the `blocker_note` field is underrated. when a session stalls . agent hit a missing env var, a schema it didn't expect, an API that returned something weird . I update status to `blocked` and drop a one-liner in `blocker_note`. then my morning check is just:

```sql
SELECT id, goal, blocker_note FROM sessions WHERE status = 'blocked';
```

instead of reading 15 terminal histories.

---

a few things that made this actually work in practice:

➡️ session IDs are human-readable slugs, not UUIDs. `enrich-apollo-003` tells me more at a glance than `a3f9b2c1`.

➡️ each Claude Code session gets its own git worktree. the worktree path goes in the table. merging back to main is a separate, deliberate step.

➡️ I log checkpoints, not just final state. mid-session the agent drops a note via a simple Python helper: `log_event(session_id, 'checkpoint', 'completed schema migration, starting seed')`. means I can see progress without reading the full thread.

➡️ the graph lives in `~/.sessions/work.db` . outside any project repo. it's infrastructure, not project state.

---

this probably sounds like overkill until you've had two agents write conflicting alembic migrations at 11pm. then it sounds like the minimum viable thing.

the full helper scripts (spin up a session, log an event, query ready-set) are pretty short . happy to drop them if there's interest.
