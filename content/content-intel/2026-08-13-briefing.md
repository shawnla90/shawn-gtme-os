```python
import json, sqlite3, pathlib

conn = sqlite3.connect("claude_history.db")

 CREATE TABLE IF NOT EXISTS turns (
 session_id TEXT,
 role TEXT,
 content TEXT,
 timestamp TEXT
 )

base = pathlib.Path.home() / ".claude" / "projects"
for f in base.rglob("*.jsonl"):
 session_id = f.stem
 for line in f.read_text().splitlines():

 content = str(turn.get("content", ""))
 ts = turn.get("timestamp", "")
 conn.execute(
```

## 8. [RESOURCE_SHARE] how I run 3-4 parallel Claude Code sessions without losing context — the actual system

**Thesis:** A concrete session management system with named worktrees, project-scoped CLAUDE.md files, and a status file each agent writes to — so you always know what each session owns.
**Target sub:** r/r/ClaudeCode
**Scores:** viral=8 voice=9 gap=8 effort=medium

### REDDIT Version

how I run 3-4 parallel Claude Code sessions without losing context . the actual system

been running 3-4 Claude Code sessions in parallel for a few months now. the context problem is real . you forget which session owns what, agents step on each other, and by session 3 you're just guessing.

here's the system that actually fixed it.

**three pieces: named worktrees, scoped CLAUDE.md files, and a status file each agent writes to**

---

**1. named git worktrees (not branches, worktrees)**

```bash
git worktree add ../myproject-feat-auth feat/auth
git worktree add ../myproject-infra feat/infra
git worktree add ../myproject-ui feat/ui
```

each session gets its own working directory. no shared filesystem state. Claude Code in session A literally cannot touch session B's files because they're separate trees.

naming convention matters: `projectname-shortlabel`. you'll be reading these in your terminal split panes constantly, so keep them short.

---

**2. project-scoped CLAUDE.md in each worktree**

each worktree gets its own `CLAUDE.md` at root level with three things:

```
## ownership
this session owns: /src/auth/** and /lib/tokens/**
do not touch: anything outside these paths

## current task
implementing jwt refresh flow . see issue #42

## handoff notes
auth middleware is complete, tokens.ts needs the rotate() method
```

the ownership block is the key piece. without it, Claude will helpfully "fix" something in a file another session is mid-way through changing. the scoped CLAUDE.md makes the boundary explicit.

---

**3. a shared status file each agent writes to**

one file at the repo root that never gets committed (add to .gitignore):

```
/tmp/session-status.md
```

at the start of each session, I tell Claude: "update /tmp/session-status.md with your current task and any blockers before we start."

the file ends up looking like:

```
## session: feat-auth (port 3001)
task: jwt refresh . tokens.rotate() method
status: in progress
last updated: 14:32
blocker: none

## session: feat-infra (port 3002) 
task: railway deploy config
```

## 10. [CONTRARIAN] hitting the usage limit every day isn't a Claude problem. it's a workflow problem.

**Thesis:** Constant limit exhaustion is a signal you're using a frontier model for tasks a smaller model handles fine. The fix isn't a bigger plan — it's a smarter routing layer between models.
**Target sub:** r/r/ClaudeCode
**Scores:** viral=8 voice=9 gap=8 effort=low

### REDDIT Version

hitting the usage limit every day isn't a Claude problem. it's a workflow problem.

I used to burn through my limit by noon and blame Anthropic. then I looked at what I was actually sending to Sonnet and felt a little embarrassed.

here's what the audit looked like: file reads, reformatting tasks, simple grep-and-summarize jobs, repetitive code stubs, docstring generation. all running through a frontier model because it was already open in the terminal and it was easy. that's not a compute bottleneck, that's lazy routing.

the fix I run now:

anything that doesn't require reasoning gets classified first. I have a small router script that checks task type before it hits Claude. the categories:

- structured extraction (JSON from messy text, schema mapping) → Haiku
- short code gen with a clear spec → Haiku or local model via Ollama
- reformatting, summarizing, diff-reading → Haiku
- multi-file reasoning, debugging with no obvious error, architecture decisions → Sonnet
- the genuinely hard stuff where I need Sonnet to think, not just output → that's when the limit matters

the router isn't fancy. it's a short prompt that classifies the incoming task type and routes accordingly. takes maybe 200ms overhead. saves probably 60-70% of my Sonnet calls.

the other thing that helped: compress your context aggressively before a session. I was reloading the same 3,000 lines of project context every conversation. now I keep a living `CONTEXT.md` that's a tight 400-word summary of what's relevant today. Claude reads less, reasons the same.

if you're hitting the limit daily, the question worth asking isn't "how do I get more" . it's "which of these tasks actually needed Sonnet." nine times out of ten the answer surprises you.

would be curious if anyone's built a smarter version of this router. mine works but it's basically a big conditional. there's probably a cleaner pattern.

### LINKEDIN Version

hitting the usage limit every day isn't a Claude problem.

it's a workflow problem.

I've watched people complain about Claude's limits while running Haiku-level tasks through Opus. File summarization. JSON formatting. Regex rewrites. Simple classification calls.

That's like using a torque wrench to hang a picture frame.

The real issue: no routing layer.

Most builders treat frontier models as the default for everything. One model, one API key, every task. It feels simple. It's actually expensive and slow.

What actually works:

route by task complexity, not by habit. Anything with structured output, light formatting, or repetitive pattern work goes to a smaller, faster model. Reserve the frontier model for reasoning-heavy calls . multi-step logic, novel synthesis, judgment under ambiguity.

I built a simple classifier in front of my agent stack. It takes the incoming task, scores it on a 1-3 complexity scale, and routes accordingly. Two hours of setup. Usage limits haven't been a daily friction point since.

the limit is data. it's telling you your architecture is flat when it should be layered.

most AI workflow problems aren't model problems. they're design problems.
