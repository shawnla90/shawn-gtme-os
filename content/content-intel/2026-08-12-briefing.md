**question 1: are you reasoning or executing?**

reasoning (debugging unknown root causes, architecture decisions, figuring out why a system behaves in a way you didn't expect) → opus

execution (implement this spec, write these tests, refactor this function using this pattern) → sonnet

I've started putting this directly in my session prompts. "you are executing, not reasoning. implement the spec exactly as written." sonnet responds to that instruction well. it stops exploring alternatives and just builds.

the mistake people make is defaulting to opus because it feels safer. it's not. for execution tasks opus second-guesses more, not less. you get more "I noticed you might also want to consider..." when you just needed the function written.

**question 2: how deep is your context?**

under 50k tokens, fresh-ish session → sonnet 
over 50k, multiple large files loaded, 30+ minutes into a complex session → opus

the context retrieval quality on longer sessions is where opus actually earns its cost. under that threshold you're paying for headroom you're not using.

**question 3: is this task something a smart junior could handle?**

yes → haiku 
no → see above

renaming variables, updating comments, writing boilerplate, generating repetitive test cases. haiku handles all of it and it's fast. save the expensive context for the hard parts.

- the model keeps asking clarifying questions instead of building → sonnet + "execute now"
- I've tried 2+ approaches on a root cause and nothing's landing → opus + full error trace, let it reason through it
- I hit a boring implementation stretch after a hard debugging session → drop to sonnet, opus context saved for when it matters again

---

the actual default: sonnet for 80% of sessions. opus when the problem is genuinely hard. haiku for anything repetitive.

1 in 4 vibe-coded apps has the .env file sitting in a public repo. here's a 10-minute pre-ship checklist.

---

shipping fast is the point. shipping your OpenAI key to a public GitHub repo is not.

I've reviewed a lot of vibe-coded projects in the wild. the pattern is always the same: the app is clever, the build is fast, and the .env file is sitting right there in the commit history. sometimes it's been there for six months.

here's the thing . GitGuardian scans public repos constantly. so does every credential-harvesting bot on the internet. within minutes of a key hitting a public repo, it's being tested against the API.

ten minutes before you push. that's all this takes.

---

**the checklist:**

**1. confirm .gitignore exists and actually works (2 min)**

```bash
cat .gitignore | grep .env
```

if that returns nothing, add it now:

```bash
echo ".env" >> .gitignore
echo ".env.local" >> .gitignore
echo ".env*.local" >> .gitignore
```

then verify git isn't already tracking it:

```bash
git ls-files | grep .env
```

if your .env shows up there, git is tracking it even with .gitignore present. fix it:

```bash
git rm --cached .env
```

**2. scan your commit history (2 min)**

adding .gitignore now doesn't erase what's already in your history. run this:

```bash
git log --all --full-history -- "**/.env*"
```

if commits show up, your key has already shipped. rotate it immediately, then decide if you want to purge the history with `git filter-repo` or just rotate and move on.

**3. grep for hardcoded secrets in the codebase (2 min)**

agents will sometimes inline a key instead of referencing the env var. happens more than you'd think.

```bash
grep -r "sk-" . --include="*.js" --include="*.ts" --include="*.py" | grep -v node_modules
grep -r "AIza" . --include="*.js" --include="*.ts" --include="*.py" | grep -v node_modules
```

adjust the prefixes for whatever APIs you're using. OpenAI keys start with `sk-`, Google keys with `AIza`, Anthropic with `sk-ant-`.

**4. check your frontend bundle isn't leaking env vars (2 min)**

if you're on Next.js or Vite, any env var prefixed with `NEXT_PUBLIC_` or `VITE_` gets bundled into the client. that means it ships to the browser.

```bash
grep -r "NEXT_PUBLIC_" .env
grep -r "VITE_" .env
```

server-only keys (database URLs, secret API keys) should never have those prefixes. if they do, rename them.

**5. verify your deployment platform isn't committing secrets (2 min)**

Railway, Render, Vercel . they all have environment variable UIs for a reason. your keys should live there, not in a `.env` file committed to the repo.

double-check your deployment config files:

```bash
cat railway.toml
cat render.yaml
cat vercel.json
```

none of those should contain actual secret values. only variable references.

---

bonus: add a pre-commit hook so this runs automatically before every push

```bash
# .git/hooks/pre-commit
#!/bin/sh
if git diff --cached --name-only | grep -q "\.env"; then
 echo "ERROR: .env file staged for commit. aborting."
 exit 1
fi
```

`chmod +x .git/hooks/pre-commit` and you're done. it'll catch you before you ship it.

---

none of this is complex. it's just the kind of thing that gets skipped when you're in flow and racing to ship.

ten minutes now vs. rotating every API key you have and auditing what got harvested. easy trade.

been running Claude Code daily across 6+ active projects for about three months. the complaints I kept seeing (and having myself) . context drift, repetitive corrections, agent going off-rails mid-session . almost all traced back to CLAUDE.md problems, not model problems.

here's the structure I landed on after a lot of trial and error:

---

**what the file actually needs to do**

CLAUDE.md isn't documentation. it's a working agreement. the model reads it at session start and uses it to calibrate behavior. if you write it like a README, you get README behavior . comprehensive but ignored when it matters.

I write mine like I'm briefing a contractor who's smart but new to this specific codebase.

---

**the sections that actually matter**

`# System` . two or three sentences max. what this project does, who it's for, what "done" looks like. I got verbose here early on and it made the agent worse, not better. less is more.

`# Stack` . exact tool names, versions if they matter, framework conventions. this prevents the agent from defaulting to its training preferences instead of yours. I had it keep reaching for Express on a Fastify project until I put this in explicitly.

`# Doing tasks` . behavioral rules. this is where most of the value lives. mine looks like:

```
- Read before editing. Never suggest changes to files you haven't opened.
- Don't create new files unless absolutely necessary. Prefer editing existing ones.
- Mark todos complete immediately when done. Don't batch.
- Never auto-commit without confirmation.
```

`# Anti-patterns` . things to never do, specific to this project. mine has things like "never use any as a TypeScript type" and "don't touch the auth middleware without asking first." the more project-specific the better.

`# Current focus` . one paragraph about what I'm actively building. I update this at the start of each session. this single section reduced my context-setting back-and-forth by probably 60%.

---

**what I stripped out**

long personality descriptions. I had a whole section trying to define the agent's "tone and style." it made responses longer and more theatrical, not better. killed it.

examples of good vs bad output. seemed useful in theory. in practice it seemed to anchor the model to the examples themselves rather than the underlying principle.

anything aspirational. "strive to write elegant code" type instructions. they don't translate to behavior. either make it a specific rule or drop it.

---

**the session-start habit that ties it together**

I keep a `# Current focus` section at the top of CLAUDE.md and update it every time I sit down. takes 30 seconds. something like:

```
# Current focus (updated 2026-08-12)
building the webhook ingestion layer for the Apollo integration.
primary file: src/webhooks/apollo.ts

```

schema looks roughly like this:

```sql
CREATE TABLE accounts (
 domain TEXT PRIMARY KEY,
 -- normal data columns --
 enriched_at TIMESTAMP,
 agent_notes TEXT, -- free text, agent writes here
 open_questions TEXT, -- what the agent flagged as unresolved
 confidence_score INTEGER, -- 1-5, agent assigns
 last_run_context TEXT -- compressed summary of what happened last session
);
```
